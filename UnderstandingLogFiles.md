# Understanding the Log Files

This document describes the structure of the log files generated by the artifact and explains how to interpret their contents.

---

# Overview

A single log file corresponds to the execution of the tool on **one benchmark**.

The tool performs **lemma generation and verification**. During each iteration, the LLM generates candidate lemmas, which are then processed and checked by the verification pipeline described in the paper. The process continues until one of the following conditions is met:

Each iteration
- The tool proves the benchmark **SAT**.
- The tool proves the benchmark **UNSAT**.
- The overall execution times out.

---

# Log File Structure

Each log file follows the structure below.

## 1. Command Invocation

The **first line** of the log file records the exact command that was executed to generate the log.

For example,

```text
uv run main.py ...
```

This allows the experiment to be get single iteration.

---

## 2. Iteration Marker

The benchmark is processed over multiple iterations.

At the beginning of every iteration, the following message is printed:

```text
Starting script iteration
```

This marker separates the output corresponding to successive iterations.

---

## 3. LLM Interaction

Following the iteration marker, the complete interaction with the language model is recorded.

This section includes:

- the prompt provided to the LLM,
- the LLM's response,
- any additional information recorded during lemma generation.

This portion of the log documents exactly which candidate lemmas were proposed during that iteration.

---

## 4. Verification Pipeline

After the LLM output, the remainder of the iteration contains the output produced by the verification pipeline.

This includes the logs generated by:

- preprocessing checks,
- syntax validation,
- lightweight testing,
- SMT solver invocations,
- lemma verification,
- Updating lemmas
- UNSAT core computation,
- and the other verification stages described in the algorithm presented in the paper.

These logs document how each generated lemma is processed and whether it is accepted, rejected, falsified, or verified.

---

# Termination Conditions

The tool continues executing iterations until one of the following conditions is satisfied.

## Successful Verification

If the tool determines that the benchmark is satisfiable or unsatisfiable, execution terminates immediately.

The corresponding verdict is recorded in the log.

## Timeout

If the overall execution exceeds the configured timeout, the process is forcefully terminated.

In both of the latter cases, no definitive verification result is obtained.

---

# Determining the Final Status

The easiest way to determine the outcome of a benchmark is to search the log file for the following strings.

| Log Entry | Final Status |
|-----------|--------------|
| `Program UNSAT` | **UNSAT** |
| `Program SAT` | **SAT** |
| Neither string appears | **UNKNOWN** |

Therefore:

- If the log contains **`Program UNSAT`**, the benchmark was successfully proved **UNSAT**.
- If the log contains **`Program SAT`**, the benchmark was successfully proved **SAT**.
- If neither string appears, the benchmark should be treated as **UNKNOWN** (typically because the execution reached the iteration limit or timed out).
